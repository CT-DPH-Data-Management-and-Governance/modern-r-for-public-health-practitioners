4  Cleaning Data

Packages covered in this part: janitor, lubridate, tidyr, stringr, glue

Real data is rarely clean. Column names are inconsistent, values need reshaping, text fields need tidying up, and dates need parsing before they’re ready for analysis. This chapter covers four packages that handle the bulk of that work.

4.1 Installing Packages

install.packages(c(
  "janitor", # for cleaning names and basic data cleaning
  "tidyr", # for reshaping data
  "stringr", # for working with text
  "glue", # for string interpolation
  "lubridate" # for working with dates
))
library(dplyr)
library(readr)
library(here)
library(janitor)
library(tidyr)
library(stringr)
library(lubridate)
library(glue)

Data come in all shapes and sizes, and it is difficult to come up with a single approach that will fit every situation. However, there are some common patterns that show up frequently in public health data. This chapter will cover some of the most common data cleaning tasks and the R packages that can help you accomplish them.

# load up our raw data
csv_path <- here("data", "raw", "ct_covid_by_town_2026-06-30.csv")
covid_data <- read_csv(csv_path)

4.2 janitor

By now you’ve probably noticed that the column names in our covid_data aren’t very easy to work with. They contain spaces and mixed case that are difficult to reference due to R’s case-sensitive nature. Other data may have special characters, punctuation, or extra white space in the names of their columns.

The janitor package has a function called clean_names() that can help with this. It will convert column names to lower case, replace spaces with underscores, and remove special characters. This makes it much easier to work with the data in R. You could recreate this functionality from scratch, but clean_names() is a convenient and well-tested function that saves time and effort and is such an easy package to recommend.

Recall the names of our covid_data:

#subset of the names
names(covid_data) |> head(5)
[1] "Last update date" "Town number"      "Town"             "Total cases"     
[5] "Confirmed cases" 
covid_clean <-
  covid_data |>
  clean_names()

names(covid_clean) |> head(5)
[1] "last_update_date" "town_number"      "town"             "total_cases"     
[5] "confirmed_cases"

A single function call - it is that simple. The janitor package has a lot of other useful functions for cleaning, and even presenting data in a more readable format. We’ll cover some of those later, but it’s worth exploring the package documentation in the callout above too.

4.3 lubridate

4.3.1 Working with Dates

Earlier in the book we covered readr’s parsing functions for reading in dates. readr is great, but there is a package whose only job is to work with dates and it makes incredibly ergonomical and intuitive.

You may have noticed that the last_update_date column in our covid_clean isn’t considered a date in R, but rather a character string. If you’re not going to be manipulating the dates, this isn’t a problem. However, if you want to do any date math - such as calculating the number of days between two dates, or filtering for dates within a certain range - you’ll need to convert the character string to a date object.

Take a look at last_update_date:

covid_clean |>
  select(last_update_date) |> # select ONLY this column
  slice(1:5) # slice the first 5 rows - kind of like head()
# A tibble: 5 × 1
  last_update_date
  <chr>           
1 06/24/2022      
2 06/24/2022      
3 06/24/2022      
4 06/24/2022      
5 06/24/2022

Date format jargon is easy to lose track of, and with lubridate you don’t have to remember it. Those dates look like the month, then the day, then the year.

We will tell lubridate that the date is in the month-day-year format by using its mdy() function and it handles the rest.

# we are going to change the character string to a date and then save the changes
# back to itself

covid_clean <-
  covid_clean |>
  mutate(last_update_date = mdy(last_update_date)) # mutate for manipulating columns

covid_clean |>
  select(last_update_date) |>
  slice(1:5)
# A tibble: 5 × 1
  last_update_date
  <date>          
1 2022-06-24      
2 2022-06-24      
3 2022-06-24      
4 2022-06-24      
5 2022-06-24

Did you catch the <date> below the column name in the output? It is a date now and can be seen in R’s standard date format. We can now do date operations on this column.

We can do simple things like this…

# how many days are in the dataset?
max(covid_clean$last_update_date) - min(covid_clean$last_update_date)
Time difference of 822 days

or more complex things like this…

# average total deaths per calendar week - demonstration purposes only

covid_clean |>
  group_by(week = floor_date(last_update_date, "week")) |> # here we are using lubridate's floor_date() to round down to the nearest week
  summarise(avg_total_deaths = mean(total_deaths, na.rm = TRUE)) |> # here we are using dplyr's summarise() to calculate the average total deaths per week
  slice(1:5)
# A tibble: 5 × 2
  week       avg_total_deaths
  <date>                <dbl>
1 2020-03-22            0.118
2 2020-03-29            0.530
3 2020-04-05            1.95 
4 2020-04-12            4.87 
5 2020-04-19            9.01

mdy() isn’t the only parser in the family. lubridate has a parsing function for every common date order - the function name spells out the order of year (y), month (m), and day (d) that it expects in the string:

ymd("2026-06-30")
[1] "2026-06-30"
mdy("06/30/2026")
[1] "2026-06-30"
dmy("30-06-2026")
[1] "2026-06-30"

Pick whichever one matches the order used in your source data - no format string, no strptime codes to look up.

It is important to keep in mind what folks want to do with these data and then clean them in a manner that will make it easier to do those things.

4.3.2 Converting to dates with as_date()

Sometimes a column is already a date-time (POSIXct), with hours, minutes, and seconds attached, but the analysis only needs the calendar date. as_date() truncates it:

now() # a datetime, with a time attached
[1] "2026-07-24 15:18:18 EDT"
now() |> as_date() # a calendar date, time dropped
[1] "2026-07-24"

4.3.3 Pulling out the day of the week with wday()

CT DPH published new case counts on a schedule, and gaps or slowdowns in reporting often line up with weekends. wday() extracts the day of the week from a date, and label = TRUE gives you a readable name instead of a number:

covid_clean |>
  distinct(last_update_date) |>
  mutate(day_of_week = wday(last_update_date, label = TRUE)) |>
  count(day_of_week)
# A tibble: 7 × 2
  day_of_week     n
  <ord>       <int>
1 Sun            57
2 Mon           112
3 Tue           118
4 Wed           117
5 Thu           115
6 Fri            72
7 Sat            14

That count is a quick way to check whether report dates cluster on certain days of the week - useful for spotting reporting cadence, or gaps, before you build anything downstream that assumes daily data.

TipThe lubridate family, at a glance
Function What it does
ymd(), mdy(), dmy() Parse a character string into a date, given the order of year/month/day
as_date() Convert a datetime (POSIXct) down to a calendar date
wday(x, label = TRUE) Extract the day of the week as a name
floor_date(x, "week") Round a date down to the start of its week

4.4 tidyr

tidyr is a wonderful package for creating and reshaping tidy data.

Pivoting data is a common usecase for tidyr. Our covid_clean dataset as-is, is probably fine for most usecases. However, it was not uncommon for similar data to be presented in a wider format during the pandemic. Let’s purposely un-tidy our data by making it wide and use the town names as the column names, something that should be a value in the data. We will then take our wide ‘messy’ data and make it tidy again in a longer format.

4.4.1 Reshaping with pivot_wider() and pivot_longer()

pivot_wider() takes a longer dataset and makes it wider.

wide <-
  covid_clean |>
  pivot_wider(
    id_cols = last_update_date, # this uniquely identifies each row in the dataset
    names_from = town, # think to yourself, "what do I want to use as the new column names?"
    values_from = total_cases, # think to yourself, "what do I want to use as the values in the new columns?"
    names_prefix = "cases_"
  ) |>
  clean_names()

wide |>
  head()

4.4.2 Handling missing values with drop_na() and replace_na()

Not every column was filled in from day one. Early in the pandemic, CT DPH hadn’t started splitting cases into confirmed vs. probable yet - confirmed_cases and probable_cases are NA for the earliest reports.

covid_clean |>
  summarise(missing_confirmed = sum(is.na(confirmed_cases)))
# A tibble: 1 × 1
  missing_confirmed
              <int>
1             11492

That’s a real gap, not a typo, and you have two honest ways to handle it depending on what comes next.

drop_na() removes rows missing a given column - use it when an analysis genuinely needs the confirmed/probable breakdown and rows without it can’t contribute:

covid_clean |>
  drop_na(confirmed_cases) |>
  nrow()
[1] 90753

replace_na() keeps every row and fills the gap with a value you choose:

covid_clean |>
  replace_na(list(confirmed_cases = 0, probable_cases = 0)) |>
  select(last_update_date, confirmed_cases, probable_cases) |>
  head()
# A tibble: 6 × 3
  last_update_date confirmed_cases probable_cases
  <date>                     <dbl>          <dbl>
1 2022-06-24                   439             75
2 2022-06-24                  4222            689
3 2022-06-24                   671             73
4 2022-06-24                  2773            257
5 2022-06-24                   490             37
6 2022-06-24                  1163            143
Warning

Filling NA with 0 says “this was measured, and the answer was zero.” That’s not what happened here - the confirmed/probable split simply wasn’t being tracked yet. Replacing with 0 would make early 2020 look like it had zero confirmed cases, which is misleading in a public health report. drop_na() or leaving the NA in place is usually the more honest choice; only reach for replace_na() when missing genuinely does mean the same thing as zero (or whatever value you’re filling in with).

4.4.3 Splitting and combining columns with separate() and unite()

Sometimes several pieces of information need to travel together in one column - a “2026-06” style label for grouping by month, for example. unite() glues columns together with a separator:

dates_split <-
  covid_clean |>
  mutate(
    report_year = year(last_update_date),
    report_month = month(last_update_date)
  ) |>
  select(last_update_date, report_year, report_month) |>
  distinct()

dates_united <-
  dates_split |>
  unite(col = "year_month", report_year, report_month, sep = "-", remove = FALSE)

dates_united |>
  head()
# A tibble: 6 × 4
  last_update_date year_month report_year report_month
  <date>           <chr>            <dbl>        <dbl>
1 2022-06-24       2022-6            2022            6
2 2022-06-23       2022-6            2022            6
3 2022-06-22       2022-6            2022            6
4 2022-06-21       2022-6            2022            6
5 2022-06-20       2022-6            2022            6
6 2022-06-17       2022-6            2022            6

separate() does the reverse - split one column into several using a separator to know where to break it apart:

dates_united |>
  select(last_update_date, year_month) |>
  separate(col = year_month, into = c("year", "month"), sep = "-") |>
  head()
# A tibble: 6 × 3
  last_update_date year  month
  <date>           <chr> <chr>
1 2022-06-24       2022  6    
2 2022-06-23       2022  6    
3 2022-06-22       2022  6    
4 2022-06-21       2022  6    
5 2022-06-20       2022  6    
6 2022-06-17       2022  6

Just like the wide/long round trip earlier, unite() and separate() are inverses of each other - whichever shape a report or a join needs, the other function gets you back.

4.5 stringr and glue

Public health data is full of free text - town names, facility names, notes fields, category labels typed by different people at different times. stringr gives you consistent functions for detecting, replacing, and reshaping that text. glue turns data into sentences, useful for report text, labels, and messages that need to fill in with real values from your dataset instead of being copy-pasted by hand.

4.5.1 Detecting patterns with str_detect()

str_detect() returns TRUE/FALSE for whether a pattern appears in each string. Use it inside filter() to keep only rows that match.

covid_clean |>
  distinct(town) |>
  filter(str_detect(town, "New"))
# A tibble: 9 × 1
  town         
  <chr>        
1 New Britain  
2 New Canaan   
3 New Fairfield
4 New Hartford 
5 New Haven    
6 Newington    
7 New London   
8 New Milford  
9 Newtown

That caught more than towns actually named “New Something” - Newington and Newtown matched too, because str_detect() looks for the pattern anywhere in the string. Anchor the pattern to the start with ^ and require a space after “New” to match only the compound names:

covid_clean |>
  distinct(town) |>
  filter(str_detect(town, "^New "))
# A tibble: 7 × 1
  town         
  <chr>        
1 New Britain  
2 New Canaan   
3 New Fairfield
4 New Hartford 
5 New Haven    
6 New London   
7 New Milford

4.5.2 Changing case with str_to_title() and friends

Data entered by hand rarely agrees on case. str_to_upper(), str_to_lower(), and str_to_title() normalize it:

"HARTFORD" |> str_to_title()
[1] "Hartford"
"hartford" |> str_to_upper()
[1] "HARTFORD"
"Hartford" |> str_to_lower()
[1] "hartford"

Reach for str_to_title() when preparing labels for a plot or report where you want consistent, presentable capitalization no matter how the value happened to be stored.

4.5.3 Trimming whitespace with str_trim()

Stray leading or trailing whitespace is invisible in a viewer but breaks joins and comparisons. str_trim() removes it:

"  Hartford   " |> str_trim()
[1] "Hartford"

If a filter() or a join isn’t matching rows you know should match, whitespace like this is one of the first things worth checking.

4.5.4 Replacing values with str_replace()

str_replace() swaps the first match of a pattern; str_replace_all() swaps every match. Both take the same three arguments: the string, the pattern to find, and the replacement.

covid_clean |>
  distinct(town) |>
  filter(str_detect(town, "^New ")) |>
  mutate(short_name = str_replace(town, "^New ", "N. "))
# A tibble: 7 × 2
  town          short_name  
  <chr>         <chr>       
1 New Britain   N. Britain  
2 New Canaan    N. Canaan   
3 New Fairfield N. Fairfield
4 New Hartford  N. Hartford 
5 New Haven     N. Haven    
6 New London    N. London   
7 New Milford   N. Milford

4.5.5 Building sentences with glue()

glue() interpolates R values directly into a string. Wrap any expression in {} and it is evaluated and inserted in place:

town_name <- "Hartford"

case_count <-
  covid_clean |>
  filter(town == town_name, last_update_date == max(last_update_date)) |>
  pull(total_cases)

glue("As of the latest report, {town_name} had {case_count} total cases.")
As of the latest report, Hartford had 33844 total cases.

glue() also works row-by-row against a data frame column, which is the more common way you’ll use it in practice:

covid_clean |>
  filter(last_update_date == max(last_update_date)) |>
  slice(1:3) |>
  mutate(
    summary = glue("{town}: {total_cases} total cases, {total_deaths} deaths")
  ) |>
  pull(summary)
Andover: 514 total cases, 6 deaths
Ansonia: 4911 total cases, 49 deaths
Ashford: 744 total cases, 5 deaths

This is the kind of line that goes straight into an automated report - no manually copying numbers into a sentence, and no risk of a stale number left over from last week’s version.
